## 2. Executive Architecture Summary

ANEI is a single Next.js 16 App Router application serving both the public/marketing site and an authenticated learner + admin experience, backed by PostgreSQL (Drizzle ORM) and Redis, used for both rate limiting (`src/server/security/rate-limit.ts`) and read-through query caching of the heavy admin user list/detail queries (`src/modules/admin/queries/admin-users.ts`, 60s TTL — VERIFIED, see §19). Auth is Better Auth with email/password + optional Google OAuth, role stored on the `user` row (`USER`/`ADMIN`/`SUPER_ADMIN`) plus a granular permission layer for admin routes. Payments are pluggable (`mock`, `flouci`, `clicktopay`-stub) behind a `PaymentGateway` interface; all payment status transitions are re-verified server-to-server against the provider — client/webhook-claimed status is never trusted directly. Private course video/documents and paid resources are served via time-limited S3-compatible signed URLs, gated by entitlement checks performed in the query layer (not in the storage module itself). The app is bilingual (French default, Arabic with RTL) via a `[locale]` URL segment, with locale/CSP/admin-header logic centralized in `src/proxy.ts` (Next middleware). Deployment target is a standalone Next.js server in Docker; CI runs typecheck/lint/unit/integration/security-audit/build/E2E via GitHub Actions plus a weekly CodeQL scan.

## 5. Architecture & Dependency Map

Request flow (typical protected mutation):
`route.ts` → `isTrustedMutation()` (origin/CSRF) → `getSession()`/`getAdminSession()`/`getAdminSessionFor(permission)` (auth+authz) → `consumeRateLimit()`/`adminMutationRateLimit()` (Redis or in-memory fallback) → `readLimitedJson()` + Zod schema (input validation) → service/query layer (Drizzle, often `db.transaction`) → PostgreSQL → (optional) external provider (Flouci, SMTP, S3) → JSON response, with `auditLogs` insert for admin/money-moving actions.

Pages follow: `page.tsx` (async server component) → `requireUser`/`requireAdmin`/`requireAdminPermission` (redirect-based) → query module → render, with interactive leaf components marked `"use client"`.

## 6. Frontend Architecture

- App Router with a `[locale]` dynamic segment (`fr`/`ar`) as the only i18n mechanism — no subdomain/cookie-based locale. `src/app/[locale]/layout.tsx` validates locale via `isLocale()` and wraps pages with `SiteHeader`/`SiteFooter` unless the proxy-stamped `x-anei-admin` header is `"1"`.
- No `middleware.ts`; `src/proxy.ts` performs the equivalent job (locale detection, nonce-based strict CSP, `x-anei-admin` header), explicitly excluding `/api` from its matcher — API routes therefore do all of their own auth.
- Public routes: `about`, `actualites`, `avs`, `bibliotheque`, `certificats`, `conditions`, `confidentialite`, `contact`, `formations/[slug]`, `webinaires`.
- Auth pages: `login`, `register`, `forgot-password`, `reset-password`, driving Better Auth's `authClient` directly from client components (no server actions).
- Learner: `dashboard`, `dashboard/profil`, `apprendre/[slug]` (video lesson player, progress PUT to `/api/progress`).
- Admin: `admin/{users,courses,enrollments,certificates,webinars,resources,news,orders,payments,contacts,audit,system,learning}` plus two legacy French-slug redirect routes (`utilisateurs` → `users`, `commandes` → `orders`).

RTL handled via CSS logical properties (`inset-inline-start/end`) plus `dir="rtl"` set at both root `<html>` and `.app-shell`.
- Forms/validation: client components call API routes via `fetch` or the Better Auth client SDK; **no Next.js Server Actions found** (`grep '"use server"'` across `src` = 0 matches). Server-side validation is Zod on every API route sampled.
- Client/server boundary: pages are server components by default (mostly `export const dynamic = "force-dynamic"`); interactivity isolated to `"use client"` leaves (`VideoLessonPlayer`, `AuthForm`, `AdminUserCrmActions`, `AdminShell`, `CheckoutButton`).
- i18n string strategy: a small shared `copy` object in `src/lib/i18n.ts` for nav/common strings, plus per-component inline `ar ? "..." : "..."` ternaries for page-specific copy — no message-catalog library (`next-intl`/`i18next` not used), no pluralization/interpolation system.

## 8. Authentication

- `src/server/auth/index.ts` configures `betterAuth()` with `drizzleAdapter(db, { provider: "pg", schema })`.
- Providers: email/password (min 10 / max 128 chars, `revokeSessionsOnPasswordReset: true`) and optional Google OAuth + One Tap, both gated by `env.ENABLE_GOOGLE_AUTH`/`googleAuthConfigured`.
- Custom `user` fields: `role` (`input: false` — cannot be set by the client), `locale`, `profileType`.
- `databaseHooks.user.create.before` → `enforceNewUserDefaults()` (`src/server/auth/policy.ts`) force-overwrites `role: "USER"` on every new user (including OAuth/One Tap sign-ups), preventing client-side privilege self-elevation at registration.
- **VERIFIED**: Better Auth's own rate limiting is enabled with `storage: "database"` (`src/server/auth/index.ts:99`), i.e. it genuinely uses the DB-backed `rateLimit` table (schema.ts:104) that the `drizzleAdapter` schema exposes to it — this is not vestigial. `window: 60, max: 120` globally, plus `customRules` tightening `/sign-in/email` (8/60s), `/sign-in/social` (10/60s), `/sign-up/email` (5/60s), `/request-password-reset` (5/300s). This protects only Better Auth's own `/api/auth/*` endpoints. It is a separate, non-overlapping layer from the app's own Redis-based `consumeRateLimit` (`src/server/security/rate-limit.ts`), which protects the custom `src/app/api/**` route handlers (admin mutations, payments, progress, contact, etc.) — see §19.
- `useSecureCookies: true` in production (with a documented local-production-smoke escape hatch).

## 9. Sessions

- `src/server/auth/session.ts`: `getSession()` reads via `auth.api.getSession({ headers })` server-side.
- `requireUser(locale)` — redirect to `/login` if unauthenticated.
- `requireAdmin(locale)` — redirect unless role is `ADMIN`/`SUPER_ADMIN`.
- `requireAdminPermission(locale, permission)` — redirect unless `hasAdminPermission(role, permission)`.
- Session config: `expiresIn` 7 days, rolling `updateAge` 1 day, `cookieCache` enabled (60s maxAge).
- **Role downgrade / session revocation** — findings, precisely scoped by evidence strength:
  - **VERIFIED**: `PATCH /api/admin/users/[id]/role` (`src/app/api/admin/users/[id]/role/route.ts`) updates `user.role` in a transaction and inserts an `auditLogs` row, but contains **no call to any Better Auth session-revocation API** (grepped the full file — only `revokeSessionsOnPasswordReset: true` exists elsewhere, in `auth/index.ts`, scoped to password resets, not role changes). The underlying `session` table row for the demoted user is left untouched. No explicit session revocation occurs anywhere in the role-change flow.
  - **VERIFIED**: `cookieCache.maxAge` is configured to 60 seconds (`auth/index.ts:92`).
  - **INFERENCE**: because Better Auth's `cookieCache` is enabled with a 60s window and no revocation occurs, stale role information (the pre-downgrade role) may plausibly continue to be served from the cached session cookie for some period after a downgrade, without a fresh DB read.
  - **UNKNOWN**: Better Auth's exact internal cookie-cache refresh/revalidation behavior (e.g., whether it strictly expires and re-fetches at 60s, revalidates opportunistically, or has other internal triggers) was not inspected in Better Auth's own source/dependency code — only the `maxAge: 60` config value on this project's side is confirmed. The precise real-world duration of stale-role exposure is therefore **not proven** and should not be cited as an exact "up to 60 seconds" guarantee without inspecting Better Auth's internal implementation.

## 10. Authorization & Permission Model

- Roles: `"USER" | "ADMIN" | "SUPER_ADMIN"` stored on `user.role` (schema.ts:22).
- Granular permissions defined in `src/modules/admin/domain/permissions.ts`: `adminPermissions` — 25 string-literal permissions (`overview.read`, `users.read`, `users.manage`, `users.role.change`, `courses.read/create/update/publish/delete`, `enrollments.read`, `learning.read`, `certificates.read`, `webinars.read/manage`, `resources.read/manage`, `news.read/manage`, `orders.read`, `payments.read`, `payments.reconcile`, `contacts.read/manage`, `audit.read`, `system.read`).
- `hasAdminPermission(role, permission)`: `SUPER_ADMIN` → always `true`; `ADMIN` → `true` only if permission is in the `adminCapabilities` Set.
- **VERIFIED inconsistency**: `adminCapabilities` omits `"users.role.change"` and `"courses.delete"` — these two permissions exist in the type but can never be granted to a plain `ADMIN` via `hasAdminPermission`. The role-change route (`src/app/api/admin/users/[id]/role/route.ts`) correctly enforces this in practice by calling `getSuperAdminSession()` directly rather than `getAdminSessionFor("users.role.change")` — so behavior is safe, but the permission constants are misleading/dead for those two entries.
- Admin session helpers (`src/server/auth/admin.ts`): `getAdminSession()`, `getSuperAdminSession()`, `getAdminSessionFor(permission)`, `adminMutationRateLimit(userId)` (120 req/60s via `consumeRateLimit`, applied even to authenticated admins).

## 11. Security Architecture

- **Origin/CSRF**: `isTrustedMutation(request)` (`src/server/security/origin.ts`) → `isTrustedMutationHeaders()` (`src/lib/security/origin-policy.ts`, unit-tested in `tests/unit/origin.test.ts`). Rejects `sec-fetch-site: cross-site`; validates `Origin` against `env.TRUSTED_ORIGINS`; falls back to `Referer`; if neither header present, only allows when `sec-fetch-site` is absent/`none`/`same-origin`.
- **Rate limiting**: `consumeRateLimit(key, limit, windowSeconds)` (`src/server/security/rate-limit.ts`) — atomic Redis Lua `INCR`+`EXPIRE`, falls back to an in-process `Map` (capped at 10,000 entries) on any Redis error, silently — this is a real degradation mode under Redis outage in multi-instance deployments (per-instance limiting only), not currently logged/alerted.
- **Request body limits**: `readLimitedJson(request, maxBytes=128*1024 default)` (`src/server/security/request-body.ts`) checks `Content-Length` and also streams with a byte counter to guard against a spoofed/missing header.
- **Logging redaction**: `src/server/security/logger.ts` redacts keys matching `/password|secret|token|authorization|cookie|api[-_]?key|refresh|access/i`, depth-capped recursion, truncates long strings/arrays.
- **CSP**: `src/proxy.ts` sets a per-request nonce-based strict CSP (`strict-dynamic`, `frame-ancestors 'none'`).
- **Route protection pattern** — scoped to **custom, user/admin-authenticated, state-changing `src/app/api/**` routes** (consistent across every such route sampled): origin check → auth/permission check → rate limit → Zod validation → business logic → audit log. Concrete examples: `src/app/api/admin/orders/[id]/reconcile/route.ts`, `src/app/api/admin/users/[id]/role/route.ts` (also uses `pg_advisory_xact_lock` to guard the "last super admin" invariant), `src/app/api/payments/verify/route.ts`.
- **This pattern does not apply uniformly to every mutation-capable endpoint.** Routes with a different trust model follow a different, narrower sequence by necessity: Better Auth-managed endpoints (`/api/auth/*`) are handled entirely inside the `better-auth` library and rely on its own internal session/rate-limit/CSRF handling, not this app's `isTrustedMutation`/`consumeRateLimit`/audit-log pattern. External-provider webhooks (e.g. `src/app/api/payments/flouci/webhook/route.ts`) cannot perform an origin/session check against an unauthenticated third-party caller, and instead rely on re-verifying the claimed action server-to-server against the provider (§16) rather than the standard auth-gated sequence — see the documented gap in §16/§33 (no signature/HMAC verification on that specific webhook).
- **`x-anei-admin` header** is proxy-stamped from an unauthenticated path regex — used only for UI chrome decisions (hiding site header/footer), not as an authorization signal; actual admin authz is always re-checked server-side per route/page.
- **Static security guardrails**: `scripts/security-audit.ts` scans source for forbidden patterns (`@ts-ignore`, `dangerouslySetInnerHTML`, `eval(`, `new Function(`, `child_process`, dead `href="#"`), run in CI.

## 13. Data Access / Query / Service Patterns

- **Queries** (`src/server/queries/*`): read-only, `Promise.all`-parallelized, hand-rolled pagination (`pageBounds` in `catalog.ts`, `adminPageBounds` in `admin.ts` — near-duplicate implementations, minor technical debt), `ilike`-based search capped at 100 chars, safelisted sort/filter enums. `catalog.ts::getPublishedCourse` deliberately signs only preview lesson media and nulls `documentUrl` for public rendering paths (explicit comment: full lesson object keys never reach public paths). `account.ts::getLearningCourse` only signs media for enrolled users (joined against `enrollments`).
- **Services** (`src/server/services/*`): all mutating logic. `checkout.ts` — order creation with idempotency-key reuse, free-item auto-grant, payment verification/reconciliation, entitlement granting (`grantPaidOrderTx`, uses `onConflictDoNothing` on composite unique keys — safe to call multiple times). `progress.ts` — `updateLessonProgress` derives completion server-side from stored watched-seconds vs. duration (explicit anti-forgery rationale in comments), cascades to enrollment percent and certificate issuance in one transaction. `mailer.ts` — nodemailer wrapper with dev console-fallback (except production) and manual HTML-escaping.
- **Transactions** (VERIFIED via `grep db.transaction`, exactly 3 call sites): `checkout.ts` (`createOrderCheckout`, `applyVerification`, `markMockOrderPaid`, `grantOrder`), `progress.ts` (`updateLessonProgress`), `api/admin/users/[id]/role/route.ts` (role change, with `pg_advisory_xact_lock` for the "last super admin" invariant).
- **Idempotency**: DB-unique `orders.idempotencyKey` per user; entitlement grants use `onConflictDoNothing`; lesson progress upsert uses `onConflictDoUpdate`; certificate issuance uses `onConflictDoNothing`.

## 15. Enrollment / Progress / Certificates

- `enrollments` table links user↔course, unique per pair; created by `grantPaidOrderTx` on successful order (or free-item auto-grant).
- `lessonProgress` tracks per-lesson watched seconds, unique per (enrollment, lesson), upserted via `onConflictDoUpdate`.

## 16. Payments / Orders / Entitlements

- `PaymentGateway` interface (`src/server/payments/types.ts`): `isConfigured()`, `createCheckout()`, `verify()`. Three registered providers (`src/server/payments/index.ts`): `mock`, `flouci`, `clicktopay` (stub — `isConfigured()` always `false`, both methods throw; schema already models it as a valid enum value for future activation).
- **mock** (`mock.ts`): active when `NODE_ENV !== "production" || env.PAYMENT_ALLOW_MOCK`. Uses HMAC-SHA256 token keyed on `BETTER_AUTH_SECRET`, verified with `crypto.timingSafeEqual` (length-checked first to avoid throw-on-mismatch).
- **flouci** (`flouci.ts`): `createCheckout` posts to Flouci `/api/v2/generate_payment` with a webhook URL pointing at `/api/payments/flouci/webhook`; `verify(externalPaymentId)` calls Flouci `/api/v2/verify_payment/:id`.
- **Flow**: `POST /api/payments/create` → auth + rate limit (20/60) + origin check → `createOrderCheckout` → inserts `orders` (status `pending`) → gateway `createCheckout` → inserts `payments` row with `checkoutUrl`. Free items (`amountMillimes === 0`) skip payment and are granted immediately in one transaction.
- **VERIFIED — payment verification is never trusted from client redirect or webhook payload**: `applyVerification()` (`checkout.ts`) is the single authority that flips status to `paid`, cross-checking the provider's returned `amountMillimes`/`merchantReference` against the DB-recorded order values ("Client totals never participate in this decision" — inline comment). The Flouci webhook handler (`src/app/api/payments/flouci/webhook/route.ts`) extracts **only** the `payment_id` from the incoming payload and discards any claimed status, always making a fresh server-to-server `verifyAndApplyByExternalId` call.
- **Gap (flagged by specialist, not a fraud vector)**: the Flouci webhook route has no signature/HMAC verification and no rate limit on itself — mitigated because the webhook cannot force a fraudulent "paid" state (only triggers a real re-verify), but an attacker could spam it with arbitrary `payment_id` values to trigger outbound Flouci calls (minor cost/DoS surface).
- User-facing verify endpoint (`/api/payments/verify`) requires `isTrustedMutation` + session + per-user rate limit (10/60s) + ownership check (`orders.userId === session.user.id`).
- Mock completion (`/api/payments/mock/complete`) is dev-only (gated by `mockGateway.isConfigured()`), requires `isTrustedMutation`, validates the same HMAC token minted at checkout.
- **Entitlement granting**: `grantPaidOrderTx(tx, order)` inserts into `enrollments` (course) or `purchases` (resource) via `onConflictDoNothing` on composite unique keys — idempotent regardless of how many times invoked — plus a `notifications` row and an `auditLogs` row (`action: "entitlement.granted"`) in the same transaction. Recovery path `grantOrder(orderId)` used by admin `/reconcile` only grants for orders already `paid` but missing an entitlement.

## 17. Storage & Protected Media

- `src/server/storage/index.ts`: S3-compatible client built per-call, requires `STORAGE_PROVIDER === "s3-compatible"` (throws `OBJECT_STORAGE_NOT_CONFIGURED` otherwise); production boot explicitly forbids `STORAGE_PROVIDER=local` (`env.ts`).
- `signedDownloadUrl(objectKey, filename)` — rejects absolute/http(s) keys, `Content-Disposition: attachment`, TTL from `STORAGE_DOWNLOAD_URL_TTL_SECONDS` (env-bounded 60–3600s, default 300s).
- `signedMediaUrl(objectKey)` — same key validation (also rejects leading `/`), inline disposition, TTL from `STORAGE_MEDIA_URL_TTL_SECONDS` (env-bounded 300–14400s, default 7200s).
- `validateUpload()` — MIME allowlist (6 types), per-type max size (500MB video/mp4, 25MB others).
- `signedUploadUrl()` — admin-only presigned POST, key includes category/date/UUID, server-enforced exact Content-Type + content-length-range, 300s expiry.
- **Important invariant**: the storage module performs **no entitlement check itself** — authorization happens in the calling query/route layer (e.g., `getPublishedCourse` nulls `documentUrl` for public pages; `getLearningCourse` only signs media joined against the caller's `enrollments`). Any new caller of `signedMediaUrl`/`signedDownloadUrl` must replicate this entitlement gating.

## 19. Redis / Caching / Rate Limiting

- `src/server/cache/redis.ts`: singleton client via `createClient({url})`, lazy connect (`getRedis()`), errors logged (except test env), `checkRedis()` health check.
- **VERIFIED — rate limiting**: `src/server/security/rate-limit.ts` (`consumeRateLimit`) uses Redis for atomic Lua `INCR`+`EXPIRE` rate limiting, protecting custom `src/app/api/**` route handlers (admin mutations, payments, progress, contact, etc.).
- **VERIFIED — query caching**: `src/modules/admin/queries/admin-users.ts` (`getAdminUsers`, `getAdminUserDetail`) independently uses the same `getRedis()` singleton for read-through caching of the heavy admin user list/detail SQL queries. Cache keys: `` `admin:users:list:${JSON.stringify(filter)}` `` (one entry per distinct filter/sort/page combination) and `` `admin:users:detail:${id}` ``. Both are `redis.set(cacheKey, JSON.stringify(payload), { EX: 60 })` — a flat 60-second TTL, read on a cache hit via `redis.get` with manual `Date` field rehydration. **No invalidation-on-write exists anywhere in this file or elsewhere in the codebase** (no `redis.del` call for these keys was found) — staleness is bounded purely by the 60s TTL, not by explicit invalidation when a user's role/data changes (e.g. via `/api/admin/users/[id]/role`). This confirms the commit message "perf(admin): implement redis caching for heavy admin user queries" accurately describes code that exists at HEAD.
- Both caching and rate-limiting share the same Redis client/connection but operate as independent concerns with distinct key namespaces (`admin:users:*` vs. the rate-limit counter keys) — no collision risk.
- In-memory fallback (`memoryConsume`, rate-limit only — the admin-users cache has no in-memory fallback and simply skips caching when `getRedis()` returns falsy) activates on Redis unconfigured or any Redis error (broad catch), with basic janitor eviction at 10,000 entries — a silent degradation under multi-instance deployment worth monitoring.
- **VERIFIED — separate from Better Auth's DB-backed `rateLimit` table**: Better Auth's own rate limiter (`storage: "database"`, `src/server/auth/index.ts:99`, backed by the `rateLimit` table, `schema.ts:104`) is a distinct, non-overlapping layer scoped to Better Auth's own `/api/auth/*` endpoints only (sign-in, sign-up, password reset). It does not share code, keys, or scope with either the app's Redis rate limiter or the admin-users query cache. This is intentional layering, not leftover duplication.

## 23. Important End-to-End Flows

**A. Login/session flow**
```
AuthForm (client) → authClient.signIn.email() → Better Auth handler
  → databaseHooks (role forced to USER only on create) → session cookie set
Subsequent requests: getSession() reads cookie → requireUser()/requireAdmin() redirect gates on pages;
API routes call getSession()/getAdminSession() directly.
```

**B. Admin mutation flow** (e.g. role change)
```
PATCH /api/admin/users/[id]/role
  → isTrustedMutation(request)
  → getSuperAdminSession()
  → adminMutationRateLimit(userId)
  → zod .strict() validation
  → db.transaction: pg_advisory_xact_lock (last-super-admin guard) + self-demotion guard + update
  → auditLogs insert (action: "user.role.update")
```

**C. Course purchase/payment flow**
```
CheckoutButton → POST /api/payments/create
  → isTrustedMutation + session + rate limit
  → createOrderCheckout(): idempotency-key lookup/reuse → insert orders(pending)
  → gateway.createCheckout() (Flouci/mock) → insert payments row with checkoutUrl
  → redirect user to provider checkout page
Flouci webhook POST /api/payments/flouci/webhook (payload status discarded)
  → verifyAndApplyByExternalId() → provider verify_payment API (server-to-server)
  → applyVerification(): cross-check amount/reference vs DB order → status=paid|failed
  → grantPaidOrderTx(): onConflictDoNothing insert into enrollments/purchases + notification + auditLog
```

**D. Enrollment/access flow**
```
getPublishedCourse() checks enrollment membership for the current session
  → gated UI (enroll CTA vs "continue learning")
getLearningCourse() joins enrollments to authorize which lessons' media can be signed
```

**E. Learning progress flow**
```
VideoLessonPlayer (client) → PUT /api/progress {lessonId, watchedSeconds}
  → isTrustedMutation + session + rate limit(120/60s) + zod validation
  → updateLessonProgress() [transaction]: verify enrollment ownership
      → upsert lessonProgress (onConflictDoUpdate)
      → recompute enrollment percent
      → onConflictDoNothing insert certificates if complete
```

**F. Protected resource download flow**
```
Authenticated request → query layer verifies entitlement (enrollment or purchase row exists)
  → storage.signedDownloadUrl(objectKey, filename) [key format validated, TTL-bounded]
  → client redirected to time-limited S3 URL (Content-Disposition: attachment)
```

**G. Admin content-management flow**
```
Admin page (server component) → requireAdminPermission(locale, "<domain>.read")
  → admin query module fetches list/detail
Admin mutation (client → API route) → isTrustedMutation → getAdminSessionFor(permission)
  → adminMutationRateLimit → zod validation → service/query write → auditLogs insert
```

## 27. Security-Critical Invariants

1. New users always get `role: "USER"` regardless of client input — enforced in `enforceNewUserDefaults()`, not the client (§8).
2. Every custom, user/admin-authenticated, state-changing `src/app/api/**` route follows origin check → auth/permission check → rate limit → validation, in that order (§11, §22). This invariant applies to that specific route class only — it does not describe Better Auth-managed endpoints (`/api/auth/*`, governed by Better Auth's own internal handling) or external-provider webhooks (e.g. the Flouci webhook, which cannot perform an origin/session check against an unauthenticated third party and instead relies on server-to-server re-verification, §16).
3. Payment status is never derived from client redirects or webhook payloads — always re-verified server-to-server and cross-checked against the DB-recorded order amount/reference (§16).
4. Entitlement grants are idempotent (`onConflictDoNothing` on composite unique keys) — safe to re-run from reconciliation paths (§16).
5. Storage signed-URL functions perform no entitlement check themselves — callers must gate access before invoking them (§17).
6. `orders.idempotencyKey` is uniquely constrained per user at the DB level, not just app logic (§12/§13).
7. The "last SUPER_ADMIN" cannot be demoted — enforced via `pg_advisory_xact_lock` + guard in the role-change route (§9/§21).
8. Admin mutation rate limiting applies even to already-authenticated admin sessions (§10).
9. Request bodies are size-limited both by declared `Content-Length` and actual streamed bytes (§11).
10. Mock payment provider is forbidden in production unless `PAYMENT_ALLOW_MOCK` is explicitly set (§16, §26).

## 28. Business-Critical Invariants

1. All monetary amounts are integer millimes — no floating point currency values anywhere in schema or checkout logic (§12).
2. Course/resource entitlements are the sole gate for private lesson media/downloads — public pages never receive signed URLs to non-preview content (§14/§17).
3. Lesson completion is derived server-side from watched-seconds vs. duration, not client-reported "completed" flags (§14).
4. Certificates are issued exactly once per (user, course) via `onConflictDoNothing` — re-triggering progress updates cannot duplicate certificates (§15).
5. Free items (`amountMillimes === 0`) bypass the payment gateway entirely but still go through the same transactional entitlement-granting path (§16).

## 29. Extension Patterns

**New authenticated API endpoint** (custom, user/admin-authenticated, state-changing `src/app/api/**` route): copy the pattern in `src/app/api/payments/verify/route.ts` or `src/app/api/progress/route.ts` — `isTrustedMutation()` → `getSession()` → `consumeRateLimit()` → Zod schema validation (often `.strict()`) → call a `services/`(write) or `queries/`(read) function → return typed JSON. Add a unit test alongside existing `tests/unit/*` if introducing new validation/security logic. **This pattern assumes a same-origin, cookie-authenticated caller** — it does not apply as-is to a Better Auth-managed endpoint or an external-provider webhook, which need their own trust model (see §11, §27 item 2).

**New admin endpoint**: copy `src/app/api/admin/orders/[id]/reconcile/route.ts` — add the permission string to `adminPermissions` in `src/modules/admin/domain/permissions.ts` (and to `adminCapabilities` if `ADMIN` role should have it, not just `SUPER_ADMIN`), use `getAdminSessionFor("your.permission")`, call `adminMutationRateLimit(session.user.id)`, wrap DB writes in `db.transaction` if multi-step, insert an `auditLogs` row with a clear `action` string.

**New DB table/migration**: inspect `drizzle/0003_course_modules.sql` for the numbered, backward-compatible migration convention; run `npm run db:generate` from the Drizzle schema change, review the generated SQL, add `check` constraints for enums following the `0001_integrity_constraints.sql` pattern, add composite unique indexes if idempotent writes are needed.

**New admin permission**: add the literal to `adminPermissions` in `permissions.ts`; decide whether it belongs in `adminCapabilities` (grantable to `ADMIN`) or should remain `SUPER_ADMIN`-only by omission (mirroring the existing `users.role.change`/`courses.delete` pattern) — but if omitting deliberately, gate the route with `getSuperAdminSession()` directly rather than leaving a dead/misleading permission constant.

**New page/form**: server component under `src/app/[locale]/...` fetches via a `queries/` module; if interactivity is needed, extract a `"use client"` leaf component (mirror `CheckoutButton`/`AuthForm`) that calls an API route with `fetch`. Validate on the server with Zod; there is no server-actions pattern to follow.

**New payment feature**: implement the `PaymentGateway` interface (`src/server/payments/types.ts`), register in the `gateways` map (`index.ts`), route all state transitions through `applyVerification()` in `checkout.ts` — never trust the new provider's client callback/webhook payload for status; always call the provider's server-to-server verify API.

**New LMS feature** (e.g. quizzes): follow the `courses → courseModules → lessons` hierarchy; extend `enrollments`/`lessonProgress` tables rather than inventing a parallel entitlement mechanism, since checkout/progress logic already assumes this shape.

**New protected resource**: store the object key in a DB column (mirroring `lessons.videoUrl`), gate access in a `queries/` function by checking the relevant entitlement table (`enrollments` or `purchases`) before calling `signedDownloadUrl`/`signedMediaUrl` — never call the storage functions directly from a route without an entitlement check first.

**New background/integration functionality**: `src/server/queue/contracts.ts` and `src/server/ai/contracts.ts` define the intended interfaces (job queue, LLM/retriever/tool) but have **no implementation** — a real implementation must be selected/built before this pattern can be used; do not assume a queue or AI backend currently exists.
